## 1. 닉네임 중복 조회 — 중복일 때 오류 응답이 오는지

`GET /api/v1/users/nickname/{nickname}/availability` 의 스펙은 200 + `{ available: boolean }` 입니다.
FE 는 `available === false` 면 인풋 아래에 "이미 사용 중인 닉네임입니다." 를 띄웁니다
(`src/components/onboarding/step/Step_2.tsx`).

그런데 QA 에서 중복 닉네임을 넣으면 **"닉네임 확인 중 오류가 발생했습니다."** 토스트가 뜹니다.
이 문구는 요청이 예외(비 2xx 또는 `success:false`)로 끝났을 때만 나옵니다.

확인 요청:

- 중복일 때 실제로 어떤 응답이 가나요? (상태 코드 · `error.code`)
- 스펙대로 **200 + `available:false`** 로 맞춰 주시거나, 오류로 주는 게 의도라면 **전용 코드**를
  알려 주세요. FE 가 그 코드를 "이미 사용 중인 닉네임이에요" 인라인 메시지로 붙입니다.
- 금칙어·형식 위반(`^[a-zA-Z0-9가-힣]+$`, 2~10자)도 오류로 떨어진다면 그 코드도 같이 부탁드립니다.

## 2. 회원가입 닉네임 선점 — 동시 가입

두 사람이 같은 닉네임으로 동시에 가입하면 둘 다 통과합니다. 중복 조회는 **조회만** 하고
점유하지 않기 때문에 FE 로는 막을 수 없습니다.

요청 사항:

- `POST /api/v1/users` 에서 닉네임 **유니크 제약**으로 뒤에 저장한 쪽을 실패시켜 주세요.
- 실패 시 **전용 오류 코드**(예: `1xxx NICKNAME_DUPLICATE`)를 주시면 FE 가 가입 1단계로 돌려보내고
  닉네임 인풋 아래에 "이미 사용 중인 닉네임이에요" 를 띄웁니다.
- QA 표현: "한 사람이 이미 저장을 눌러 점유했으면 다른 사람은 실패" — 선점 기준은 **가입 완료
  저장 시점**으로 충분합니다(닉네임 '저장' 버튼 시점의 임시 점유까지는 필요 없음).

## 3. 프로필 닉네임 변경 정책

`PATCH /api/v1/users/me/profile` 이 `nickname/gender/location/occupation` 을 받도록 바뀐 것 확인했습니다
(9/18 요청 반영, 감사합니다). FE 는 이번에 **닉네임·사는 곳·직업**을 편집 가능하게 엽니다.
성별·나이는 읽기 전용으로 유지합니다.

닉네임 변경 정책이 정해졌습니다(기존 "월 1회" 대체):

```
- 14일(rolling) 동안 최대 2회 변경 가능
- 진행 중인 대화방(개방 전 포함, 종료·나감 제외)이 있으면 변경 불가
```

요청 사항:

- 위 정책을 **서버에서 검증**해 주세요. FE 안내 문구만으로는 우회됩니다.
- 거절 시 **서로 다른 전용 코드** 두 개를 주세요 — 문구가 다릅니다.
  - 횟수 초과 → FE 문구: "닉네임은 14일 동안 2번까지 바꿀 수 있어요."
  - 대화 중 → FE 문구: "대화 중에는 닉네임을 바꿀 수 없어요."
- 중복 닉네임은 §2 와 **같은 코드**로 주시면 됩니다.
- (선택) `GET /api/v1/users/me/profile` 에 `nicknameChangeAvailableAt`(다음 변경 가능 시각, null=지금 가능)
  또는 남은 횟수를 주시면, 저장을 누르기 전에 미리 비활성화하고 날짜를 안내할 수 있습니다.

## 4. 평가 — "완료"와 "아직 안 열림" 구분

`GET /api/v1/member-reviews` 는 **완료하지 않은 평가만** 내려옵니다. 그래서 종료된 방의 평가가
목록에 없을 때, FE 는 둘 중 무엇인지 구분할 수 없습니다.

- 이미 평가를 끝냄 → 버튼을 "완료된 평가입니다" 로 막아야 함
- 방은 끝났지만 서버가 평가를 아직 만들지 않음(스케줄러 지연 등) → 막으면 안 됨

QA "종료된 대화방 평가하기 클릭 시 오류" 대응으로 FE 는 현재 **목록에 없으면 완료**로 봅니다.
두 번째 경우가 실제로 생기면 사용자가 평가를 못 하게 됩니다.

요청 사항(둘 중 하나):

- `GET /api/v1/member-reviews?includeCompleted=true` 처럼 **COMPLETED 도 내려 주기**
  (`MemberReviewResponse.status` 에 이미 `COMPLETED` enum 이 있습니다), 또는
- 채팅방 응답에 `reviewStatus: NONE | PENDING | COMPLETED` 추가

추가로 확인 부탁드립니다: 방이 종료된 뒤 평가가 목록에 나타나기까지 지연이 있나요? 있다면 최대 몇 분인가요?

## 5. 개방 전 방이 "종료"로 보임

QA 재현 순서: 매칭 기간 → 매칭 완료 → **대화 기간 전** 에 대화방이 "종료" 로 보임(기대: "대기중").

FE 판정(`src/features/chat/lib/roomState.ts`)은 `isEnded` → `expiresAt <= now` → `opensAt` 순서입니다.
따라서 개방 전인 방이 종료로 보였다면 서버 응답이 **`isEnded: true`** 이거나
**`expiresAt` 이 이미 지난 값**이었다는 뜻입니다.

QA 는 어드민 '시간 임시 조정'으로 이 구간을 재현했을 가능성이 큽니다. 확인 요청:

- 시간 조정 상태에서 방을 만들 때 `opensAt` / `expiresAt` 을 **실제 시각** 기준으로 계산하나요,
  **조정된 시각** 기준으로 계산하나요? 두 값의 기준이 서로 다르면 개방 전인데 만료가 지난 방이 됩니다.
- 재현된 방의 `GET /api/v1/chat/rooms/{roomId}` 응답(`isEnded`, `opensAt`, `expiresAt`, `endedReason`)을
  공유해 주세요. 응답을 보고 FE 판정 순서를 바꿀지 정합니다.

## 6. 신고 사유 다중 선택

QA: "신고 사유 하나만 선택 가능 → 다중 선택 가능하게". 현재 `CreateUserReportRequest.reason` 은
문자열 하나라 FE 만으로는 못 합니다.

요청 사항:

```
POST /api/v1/user-reports
  reasons: ReportReason[]   (1개 이상, 중복 불가)   ← reason 대체
```

- 전환 기간 동안 `reason` 단일 필드도 받아 주시면 FE 를 배포 순서와 무관하게 바꿀 수 있습니다.
- `etc` 가 포함되면 `detail` 필수(기존 6003) 규칙은 그대로 유지하면 됩니다.
- 어드민 신고 목록/상세에도 여러 사유가 보여야 합니다.

참고: 신고 시 **항상 차단**하도록 정책이 바뀌어 FE 는 `block: true` 로 고정해 보냅니다(체크박스 제거).
서버 쪽 변경은 필요 없습니다.

## 7. 대화방별 알림 끄기

라이브 스펙의 알림 설정은 사용자 단위(`/api/v1/users/me/notification-settings`)뿐입니다.

요청 사항:

```
PUT /api/v1/chat/rooms/{roomId}/notification   { muted: boolean }
```

- 채팅방 조회·목록 응답에 `muted: boolean` 을 같이 내려 주세요(방 메뉴 토글 상태 표시용).
- 음소거된 방의 `CHAT_MESSAGE` 푸시·알림센터 항목은 서버가 보내지 않아야 합니다.
  (FE 가 받고 숨기는 방식은 푸시가 이미 떠서 막을 수 없습니다.)
- 우선순위 낮음(P3). 계약만 먼저 정해 주셔도 됩니다.
